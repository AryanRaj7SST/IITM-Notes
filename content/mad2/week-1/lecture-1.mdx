<TopicSection id="applets-and-java" title="1. Java Applets and the Problem JavaScript Solved">

<KeyIdea>
Applets were powerful but isolated from the web page; JavaScript arose in that context.
</KeyIdea>

- This course relies heavily on JavaScript, so its history helps explain how it works. Knowing the restrictions lets us work around them or use modern versions that avoid them.
- Around 1995, Sun Microsystems created Java, designed to implement **applets**.
- An applet runs inside a web browser and allows rich interactivity, like a full native application in the browser.
- It runs in its own virtual machine to limit security risks, since a downloaded page must not read files or send sensitive data elsewhere. Java was therefore heavily restricted.
- An applet occupies one area of the page (the Java plugin). Inside it, everything differs from the rest of the page, including cursors and click handling, which the applet handles and the browser does not. This is powerful but completely separates the browser from the applet.

</TopicSection>

<TopicSection id="netscape-origin" title="2. Netscape, the Glue Language, and the Name">

<KeyIdea>
JavaScript began in 1995 as an easy scripting language to bind page components together.
</KeyIdea>

- Netscape Navigator was one of the best and most popular browsers of the time; it eventually evolved into Mozilla Firefox.
- A person at Netscape created a scripting language for it in 1995. The main advantage of a scripting language, as with Python, is simplicity: write code, run it through the interpreter, done.
- Purpose: a **glue language** to bind together applets and other systems assembled in a web page. It was not designed much for large-scale coding.
- Because HTML is forgiving (errors mostly pass without complaint), the language also had to be forgiving. If it kept crashing pages, users would reject it and ask for normal pages.
- Since it was designed to assist Java applets, it was called JavaScript. This led to trademark complaints (accusations of riding on Java's popularity) and a couple of other name changes, but "JavaScript" stuck. It is now as well known as Java although they have little in common except part of the name.

<TopicSection id="ajax" title="3. AJAX and the 2005 Turning Point">

<KeyIdea>
Background data fetching with JavaScript made web apps behave like desktop apps.
</KeyIdea>

- Early JavaScript was slow and limited, having been hastily built as a glue language to run in a browser.
- Around 2005 things changed dramatically, more through a new way of thinking than through changes to the language or browsers.
- **Google Maps** was a key demonstration, and Google also had **Suggest**, which gives suggestions as you type.
- Maps problem: data for the whole earth in fine detail cannot be loaded onto a phone or computer. So as you scroll or zoom, the browser keeps requesting new pieces of data from the server to fill the gaps, seamlessly in the background, using JavaScript.
- The process was described in 2005 by James Garrett and named **AJAX** (Asynchronous JavaScript and XML). The idea took off and changed how JavaScript is used.
- Result: web applications that behave like desktop applications. Compared with a static application, the user experience is nicer because only what an interaction needs is loaded, instead of a new page each time.
- This "spark that started the fire" led JavaScript to spread and evolve, and people began fixing its deficiencies. We will study background, asynchronous loading further; it is a main reason JavaScript suits modern web apps.

</TopicSection>

<TopicSection id="ecmascript" title="4. ECMAScript, ES Versions, and Feature Readiness">

<KeyIdea>
ECMAScript is the standard behind JavaScript; features are adopted as they become ready.
</KeyIdea>

- JavaScript became too popular to be tied to one browser or one company. ECMA (European Computer Manufacturers Association) developed **Standard Number 262**, which became **ECMAScript**.
- The name ECMAScript also helped avoid trademark issues with Java. ECMA is sometimes written as "Ecmascript", which is used as another name for JavaScript.
- Versions are called ES versions: ES4, ES5, ES6. **ES6 was established in 2015**, a major change that added many features.
- After ES6, there are yearly releases (around June) rather than ES7, ES8. Some features are standardised and frozen, for example ES2020, ES2021.
- **Feature readiness:** instead of asking whether a browser supports a whole release, a technical committee decides when each feature is ready. A feature then becomes part of the standard, and the only question is whether a given browser implements it.
- In this course we use a reasonably advanced, fairly new JavaScript (even features from 2020 or 2021), because compilers can convert new features so older browsers can still run them. This avoids workarounds.

</TopicSection>

<TopicSection id="old-browsers" title="5. Supporting Old Browsers: Upgrade, Electron, Polyfills">

<KeyIdea>
There are several ways to deal with browsers that lack modern features.
</KeyIdea>

- ES6 has most modern-language features: modules, good variable scoping, and class syntax (the syntax for classes is there).
- Older browsers may not support all of this. Options:
  1. Ignore old browsers and ask everyone to upgrade their OS and browser.
  2. Package a browser with the app, as Electron-based apps do. Visual Studio Code (VS Code, from Microsoft) is the example: it runs a Chrome browser in the background that is packaged with it, not your installed one. This works for real apps but makes systems heavy and can exhaust RAM if everyone does it.
  3. Use a **polyfill**: libraries that emulate newer functionality so it runs on older browsers.
- A polyfill is related to what a **compiler** does: it takes newer language constructs and modifies them so older JavaScript engines can run them.
- Because of these workarounds, the course sticks to fairly modern features, which are easier to understand and use.

<AddedByTutor>
Electron apps bundle Chromium, the open-source browser engine underlying Chrome.
</AddedByTutor>

</TopicSection>

<TopicSection id="beyond-browser" title="6. JavaScript Beyond the Browser">

<KeyIdea>
JavaScript can run on the back end with Node.js or Deno, without the DOM.
</KeyIdea>

- The language grew powerful enough to build the back end, so you could replace a Python Flask application with one written in JavaScript.
- It runs on the **Node.js** interpreter, currently the most popular back-end mechanism for JavaScript.
- **Deno** is another interpreter, with somewhat more restrictive features but also meant to be more secure.
- You are no longer limited to a browser. In Node.js, things like the **DOM** may not be directly available, because you are not always running in the context of a document. Keep this in mind.

</TopicSection>

<TopicSection id="performance" title="7. Performance: Ease of Use First">

<KeyIdea>
Ease of use was prioritised over speed, but modern engines are fast.
</KeyIdea>

- Because of its origins, ease of use took priority over performance, so JavaScript was not always the fastest.
- After years of optimisation, engines in modern browsers such as Chrome are very good, giving fairly good performance.
- JavaScript can also interface with graphics libraries and the GPU (graphics processing unit) in your system.

</TopicSection>

<TopicSection id="silent-failure" title="8. Silent Failure and Strict Mode">

<KeyIdea>
JavaScript could fail silently, which made debugging hard; strict mode helps.
</KeyIdea>

- HTML is forgiving: an error in the source is ignored and the browser displays what it can. JavaScript copied this tolerance.
- The problem: you do not know that something went wrong, and you can hardly find where, because the browser tolerates everything it can.
- Today this has changed. **`use strict`** mode is possible and strongly encouraged when writing scripts.
- Strict mode flags many such constructs during development. The code may still run best-effort in a browser, but you get many more debugging errors to understand.

</TopicSection>

<TopicSection id="ambiguous-syntax" title="9. Ambiguous Syntax, Semicolons, and Linters">

<KeyIdea>
Always put a semicolon after every statement and use a linter.
</KeyIdea>

- The language was put together quickly, so some syntax is ambiguous.
- **Automatic semicolon insertion:** you need not end every line with a semicolon, but in a couple of cases problems occur if you omit one.
- Comparison:

| Language | Rule |
| :--- | :--- |
| C | A semicolon is required after every statement. |
| Python | Semicolons are not part of the language (if used they just end a statement); indentation matters. |
| JavaScript | Semicolons are optional; if omitted, the interpreter works out where to put them. |

- Recommendation: be consistent, and in JavaScript put a semicolon after every statement to remove ambiguity.
- Other ambiguities: object literals and code blocks both use braces, and it is unclear whether a function declaration is a statement or an expression with a return value. These matter because they affect how a JavaScript file is parsed.
- Ambiguous variants are being deprecated and discouraged. When learning fresh, avoid sources of ambiguity and know what they are.
- **Linters** go through your source and suggest improvements for readability and maintainability. Get used to using them.

</TopicSection>

<TopicSection id="limited-io" title="10. Limited Input/Output and the Console">

<KeyIdea>
Running inside a browser means the language has no direct way to talk to the user.
</KeyIdea>

- JavaScript has very limited input/output support. Forms and similar elements exist, but the language itself has no straightforward way to communicate with the user.
- All errors are therefore logged to the **console**, which the developer reads and which is not directly visible to an end user.

</TopicSection>

<TopicSection id="strengths" title="11. Strengths: DOM Integration and Asynchronous Processing">

<KeyIdea>
Direct control of the page and asynchronous processing make JavaScript powerful.
</KeyIdea>

- **Close integration with the presentation layer**: the DOM (Document Object Model) and its APIs. JavaScript can directly manipulate what is seen on a page, which leads to interactive applications.
- **Asynchronous processing and the event loop** (covered in more detail later) let programs be expressed in useful ways and ultimately led to its use on the back end.

</TopicSection>

<TopicSection id="running-js" title="12. How We Run JavaScript in This Course">

<KeyIdea>
On the front end an HTML file loads the script, which needs a server and a browser.
</KeyIdea>

- JavaScript was not meant for direct scripting: unlike Python (python plus file name), there was originally no interpreter you could call that way. Node.js now exists, but we will not spend much time on it, since our focus is the front end.
- On the front end you need an HTML file that loads the JavaScript file as a script, and you embed it using HTML link notation.
- You need a server to serve the files and a browser to open them and request them.
- Depending on the browser, loading directly from the file system may not work. It depends on whether the browser can access the script as a file; if it must make a separate request, it probably will not.
- Demos use **Replit**, whose starter code gives an HTML file, a CSS file and a JavaScript script file to begin with.

</TopicSection>

<TopicSection id="dom-io" title="13. The DOM as the Interaction Layer">

<KeyIdea>
The DOM is the page structure, and JavaScript APIs can change both its content and structure.
</KeyIdea>

- The DOM is the structure of the document shown in the browser, manipulated through JS APIs.
- You can change displayed text and also the structure of the document itself, one of JavaScript's most powerful aspects.
- **Input:** clicking, text boxes where you enter data, even moving the mouse.
- **Output:** displaying text, changing colour or style, even drawing on screen.
- HTML5 has a `canvas` tag that lets you draw arbitrary things on screen.

</TopicSection>

```javascript
"use strict";

// DOM: change what the page shows
document.getElementById("title").textContent = "Hello from JavaScript";

// Console: where logs and errors go

// Semicolon pitfall: return followed by a newline
function bad() {
  return
  {
    ok: true
  };
}
console.log(bad());
```

### What Each Part Does:
- **index.html, line 6**: links the CSS file.
- **index.html, line 10**: heading that the script changes through the DOM.
- **index.html, line 11**: loads script.js with a separate request, which is why a server is preferred.
- **script.js, line 1**: turns on strict mode.
- **script.js, line 4**: DOM API call that changes the heading text.
- **script.js, line 7**: writes to the console.
- **script.js, lines 10-15**: automatic semicolon insertion ends `return` at the line break, so the object is never returned.
- **script.js, line 16**: prints the return value of `bad()`.
