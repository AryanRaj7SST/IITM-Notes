<TopicSection id="why-global-state" title="1. The State Management Problem & Prop Drilling">

<KeyIdea>
Global state management provides a single source of truth for application data that must be shared across disparate, deeply nested component branches.
</KeyIdea>

In an application like the IIT Madras Student Portal, user session state, notifications, and enrolled courses are needed across:
- The top Navbar
- The Course Dashboard
- The Exam Registration View

Passing this information down through dozens of nested components via props is fragile and unmaintainable. Centralized state stores hold shared data outside the component tree.

</TopicSection>

<TopicSection id="pinia-architecture" title="2. Pinia Core Architecture: State, Getters, Actions">

<KeyIdea>
Pinia organizes global domain state into three clear concepts: State (data), Getters (computed values), and Actions (business logic and mutations).
</KeyIdea>

Inside any component, using a Pinia store is as simple as calling a composable hook:

```html
<script setup>
import { useCourseStore } from '@/stores/courses';
import { storeToRefs } from 'pinia';

const courseStore = useCourseStore();

// storeToRefs preserves reactivity when destructuring state and getters
const { enrolledCourses, totalCredits, isLoading } = storeToRefs(courseStore);
// Actions can be destructured directly
const { enrollCourse } = courseStore;
</script>

<template>
  <div v-if="isLoading">Loading course credits...</div>
  <div v-else>
    <h2>Total Credits: {{ totalCredits }}</h2>
  </div>
</template>
```

Always use `storeToRefs()` when destructuring properties from a store to prevent breaking reactivity.

</TopicSection>

<TopicSection id="vuex-comparison" title="3. Pinia vs Vuex: Why Mutations Were Dropped">

<KeyIdea>
Pinia simplifies Vue state management by eliminating mutations, supporting multi-store modularity, and delivering first-class TypeScript inference.
</KeyIdea>

| Dimension | Legacy Vuex (v3 / v4) | Modern Pinia |
| :--- | :--- | :--- |
| **Mutation Concept** | Mandatory synchronous `commit('MUTATION')` | Eliminated; actions mutate state directly |
| **Store Structure** | Monolithic single tree with namespaced modules | Modular independent flat stores |
| **TypeScript Support** | Complex manual typing required | Automatic full type inference |
| **Boilerplate** | High (types, mutations, actions, getters) | Minimal |

Pinia is lighter (around 1.5kb) and natively integrates with the Composition API.

</TopicSection>

<TopicSection id="store-composition" title="4. Modular Store Organization and Persistence">

<KeyIdea>
Partitioning global state into dedicated domain stores (e.g. `authStore`, `courseStore`, `cartStore`) ensures clean separation of concerns and enables route-level code splitting.
</KeyIdea>

Stores can easily import and interact with one another:

```javascript
import { defineStore } from 'pinia';
import { useAuthStore } from './auth';

export const useCourseStore = defineStore('courses', {
  actions: {
    async register() {
      const auth = useAuthStore();
      if (!auth.isLoggedIn) {
        throw new Error("Must be logged in to register.");
      }
      // Use auth.token in request header
    }
  }
});
```

Third-party plugins like `pinia-plugin-persistedstate` automatically sync designated stores to browser `localStorage` or `sessionStorage`.

</TopicSection>
