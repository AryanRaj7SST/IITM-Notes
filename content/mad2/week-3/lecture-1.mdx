<TopicSection id="mpa-vs-spa" title="1. Traditional MPAs vs Single Page Applications (SPAs)">

<KeyIdea>
SPAs replace the traditional cycle of full-page server reloads with instant in-browser component swapping, delivering desktop-like fluid user experiences.
</KeyIdea>

In traditional Multi-Page Applications (MPAs) built with Django, Flask, or PHP:
1. User clicks a link.
2. The browser requests an entirely new HTML document from the server.
3. The screen flashes white while old assets are discarded and new assets are fetched and parsed.

In a Single Page Application (SPA):
1. The initial request fetches one minimal `index.html` file along with the JavaScript bundle.
2. Clicking a link updates the URL locally and dynamically fetches only raw JSON data from API endpoints.
3. The existing DOM is patched in place with zero screen flicker.

</TopicSection>

<TopicSection id="history-api" title="2. The HTML5 History API: pushState and popstate">

<KeyIdea>
The HTML5 History API allows JavaScript to manipulate the browser address bar and travel through session history programmatically.
</KeyIdea>

Before HTML5, single-page navigation relied on URL hashes (`example.com/#/courses`). The History API modernized this:

```javascript
// Adds a new entry to the history stack
history.pushState({ pageId: "courses" }, "Courses", "/courses");

// Overwrites current entry without adding to history
history.replaceState({ pageId: "courses" }, "Courses", "/courses");

// Listens to user clicking browser Back or Forward buttons
window.addEventListener("popstate", (event) => {
  console.log("Navigated to:", window.location.pathname);
});
```

`pushState` alters the URL displayed in the address bar without issuing an HTTP `GET` request to the web server.

</TopicSection>

<TopicSection id="client-side-routing" title="3. How Client-Side Routers Work Under the Hood">

<KeyIdea>
A client-side router acts as an event-driven dispatcher mapping URL patterns to specific component views.
</KeyIdea>

The operational flow of a client router:
1. Intercepts anchor tag click events globally (`preventDefault()`).
2. Calls `history.pushState()` with the target URI.
3. Matches the URI against an internal route table (e.g. `/students/:id`).
4. Extracts dynamic route parameters (`id = 42`).
5. Destroys the current view component and mounts the matching component into the router viewport.

</TopicSection>

<TopicSection id="tradeoffs" title="4. Trade-offs: Initial Load, SEO, and Server Fallback">

<KeyIdea>
While SPAs deliver unmatched runtime speed, they introduce architectural trade-offs in initial bundle size, search crawler indexing, and server routing.
</KeyIdea>

### Key Architectural Trade-offs:
- **First Contentful Paint (FCP)**: SPAs can feel slower on first load over cellular networks because the browser must download and execute the entire framework bundle before rendering.
- **Server Fallback Requirement**: Refreshing a deep link requires the web server to rewrite all requests back to `/index.html`, allowing the client router to boot and read `window.location.pathname`.
- **Search Engine Optimization (SEO)**: Traditional search bots may not wait for asynchronous API calls to populate templates before indexing text.

Modern applications address bundle size through route-level lazy loading (dynamic `import()`).

</TopicSection>
