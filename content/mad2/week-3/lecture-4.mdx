<TopicSection id="fetch-vs-axios" title="1. Native Fetch API vs Axios HTTP Client">

<KeyIdea>
Axios provides built-in defaults that streamline enterprise API communication compared to native `fetch()`, including automatic JSON serialization, request cancellation, and response unwrapping.
</KeyIdea>

| Feature | Native `window.fetch()` | Axios Client |
| :--- | :--- | :--- |
| **JSON Handling** | Manual (`await res.json()`) | Automatic serialization & parsing |
| **Error Rejection** | Only rejects on network failure (not on 4xx/5xx) | Automatically rejects on non-2xx status codes |
| **Request Timeout** | Manual via `AbortController` | Built-in `timeout: 5000` option |
| **Interceptors** | Not supported natively | Full request and response interceptor pipeline |
| **Bundle Size** | 0 KB (browser built-in) | ~13 KB |

For modern full-stack SPAs communicating with REST backends, Axios remains the industry standard.

</TopicSection>

<TopicSection id="axios-interceptors" title="2. Request and Response Interceptors">

<KeyIdea>
Interceptors centralize cross-cutting network logic, eliminating repetitive authentication headers and manual 401 token refresh routines.
</KeyIdea>

```javascript
// Request interceptor attaches auth headers
api.interceptors.request.use(config => {
  const token = authStore.token;
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});

// Response interceptor handles expired sessions globally
api.interceptors.response.use(
  response => response,
  error => {
    if (error.response?.status === 401) {
      authStore.logout();
      router.push('/login');
    }
    return Promise.reject(error);
  }
);
```

This ensures that individual component views remain clean, focusing purely on presentation logic rather than authentication tokens.

</TopicSection>

<TopicSection id="ui-lifecycle-states" title="3. Designing Loading, Success, Error, and Empty States">

<KeyIdea>
Every asynchronous UI element must cleanly reflect four distinct operational states: Loading, Success, Error, and Empty.
</KeyIdea>

A resilient template pattern using declarative Vue directives:

```html
<template>
  <div class="roster-container">
    <!-- 1. Loading State -->
    <div v-if="isLoading" class="spinner">Loading student records...</div>

    <!-- 2. Error State -->
    <div v-else-if="errorMessage" class="error-banner">
      <p>{{ errorMessage }}</p>
      <button @click="fetchData">Retry</button>
    </div>

    <!-- 3. Empty State -->
    <div v-else-if="students.length === 0" class="empty-state">
      <p>No students enrolled yet.</p>
    </div>

    <!-- 4. Success State -->
    <ul v-else class="roster-list">
      <li v-for="student in students" :key="student.id">
        {{ student.name }}
      </li>
    </ul>
  </div>
</template>
```

Testing all four states ensures that network dropouts or empty database tables do not display blank, confusing screens to students.

</TopicSection>

<TopicSection id="cors-handling" title="4. Cross-Origin Resource Sharing (CORS) in Development">

<KeyIdea>
Development proxies bypass CORS errors by forwarding requests from the frontend development server to the backend service.
</KeyIdea>

In local development, the browser considers port 5173 (Vite frontend) and port 5000 (Flask/FastAPI backend) to be different origins.

In `vite.config.js`, configure a proxy:

```javascript
export default defineConfig({
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:5000',
        changeOrigin: true
      }
    }
  }
});
```

The browser now makes requests to `http://localhost:5173/api/v1/students`, and the Vite Node server forwards it to `localhost:5000` behind the scenes, eliminating CORS preflight errors in development.

</TopicSection>
