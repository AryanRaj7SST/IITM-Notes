      import redis
      import json
      import logging
      from typing import Optional, Any

      # Initialize Redis client
      redis_client = redis.Redis(host="localhost", port=6379, db=0, decode_responses=True)

      CACHE_TTL_SECONDS = 300 # 5 minutes default TTL

      def get_cached_item(key: str) -> Optional[Any]:
          try:
              data = redis_client.get(key)
              if data:
                  logging.info(f"CACHE HIT: {key}")
                  return json.loads(data)
              logging.info(f"CACHE MISS: {key}")
              return None
          except redis.RedisError as e:
              logging.error(f"Redis get error: {e}")
              return None # Fail gracefully to database

      def set_cached_item(key: str, value: Any, ttl: int = CACHE_TTL_SECONDS):
          try:
              serialized = json.dumps(value)
              redis_client.setex(key, ttl, serialized)
          except redis.RedisError as e:
              logging.error(f"Redis set error: {e}")

      def invalidate_cache(key_pattern: str):
          try:
              keys = redis_client.keys(key_pattern)
              if keys:
                  redis_client.delete(*keys)
                  logging.info(f"Invalidated {len(keys)} keys matching '{key_pattern}'")
          except redis.RedisError as e:
              logging.error(f"Redis invalidation error: {e}")

<TopicSection id="why-caching" title="1. The Need for In-Memory Caching & Cache-Aside Pattern">

<KeyIdea>
In-memory caching stores frequently accessed query results in RAM (Redis), reducing database load and cutting API response latencies from 100ms down to sub-millisecond speeds.
</KeyIdea>

In an enterprise university portal, **90% of requests are reads** for identical, slow-changing data (course rosters, exam timetables, instructor bios).

Executing expensive SQL `JOIN` queries across 5 relational tables on every page view wastes server resources. The **Cache-Aside** pattern resolves this:

```
[ HTTP Client ] ──> [ FastAPI App ]
                          │
                   1. Check Cache?
                    ┌─────┴─────┐
            [ Cache Hit ]  [ Cache Miss ]
                 │                │
            (Return RAM)   2. Query Database (PostgreSQL)
                                  │
                           3. Store in Cache (with TTL)
                                  │
                           4. Return Response
```

</TopicSection>

<TopicSection id="cache-invalidation" title="2. Cache Invalidation and Expiration (TTL)">

<KeyIdea>
A cache is only as useful as its consistency with the source of truth; setting Time-To-Live (TTL) expiration guarantees that stale data automatically purges.
</KeyIdea>

Two primary invalidation strategies:
1. **TTL Expiration (Time-To-Live)**: Keys expire automatically after a specified duration (e.g. 5 minutes). Even if code fails to explicitly delete a key, the stale data will self-clear.
2. **Explicit Event Invalidation**: When an administrator updates a course description via `PUT /api/v1/courses/mad2`, the route handler immediately deletes the Redis key `courses:mad2`.

Combining explicit invalidation on writes with a safety TTL on reads provides a balance of performance and consistency.

</TopicSection>

<TopicSection id="redis-data-structures" title="3. Redis Data Structures: Strings, Hashes, and Sets">

<KeyIdea>
Redis offers rich data structures that allow performing complex operations (like atomic counter increments and sorted leaderboards) in memory.
</KeyIdea>

- **Strings**: Raw serialized JSON strings, session tokens, and atomic counters (`INCR api_hits`).
- **Hashes**: Mini-dictionaries representing objects (`HSET student:101 name "Alice" grade "S"`), allowing field-level updates without rewriting the whole object.
- **Sets**: Collections of unique strings (`SADD course:mad2:students "21F10001"`), enabling set operations like union and intersection.
- **Sorted Sets (ZSET)**: Sets ordered by floating-point scores, ideal for student leaderboards and sliding-window rate limiters.

</TopicSection>

<TopicSection id="celery-beat-cron" title="4. Periodic Scheduled Tasks with Celery Beat">

<KeyIdea>
Celery Beat provides a distributed alternative to OS-level crontab, coordinating recurring background maintenance tasks across server clusters.
</KeyIdea>

In `celery_app.py`, configure recurring schedules:

```python
from celery.schedules import crontab

celery_app.conf.beat_schedule = {
    # Generate daily attendance report every night at midnight IST
    "daily-attendance-summary": {
        "task": "app.tasks.reports.generate_daily_attendance",
        "schedule": crontab(hour=0, minute=0),
    },
    # Clear expired password reset tokens every 15 minutes
    "cleanup-expired-tokens": {
        "task": "app.tasks.security.purge_tokens",
        "schedule": 900.0, # 15 minutes
    },
}
```

Celery Beat tracks timing and sends task execution messages to the Redis broker, allowing available workers to execute the job without duplicate runs.

</TopicSection>
