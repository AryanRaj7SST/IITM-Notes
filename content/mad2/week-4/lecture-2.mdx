<TopicSection id="untrusted-input" title="1. The Boundary Validation Principle & Untrusted Input">

<KeyIdea>
Treat all incoming HTTP request bodies, headers, and query parameters as untrusted data that must pass rigorous schema validation before reaching business logic.
</KeyIdea>

In legacy systems lacking schema validation, developers wrote defensive guards across every route:

```python
# Fragile legacy manual validation
if "email" not in request.json:
    return {"error": "Missing email"}, 400
if not isinstance(request.json["age"], int) or request.json["age"] < 18:
    return {"error": "Invalid age"}, 400
```

This manual approach is prone to developer oversight. Schema libraries shift validation to the framework level, guaranteeing that handler functions execute only when payloads are 100% compliant.

</TopicSection>

<TopicSection id="pydantic-models" title="2. Declaring Pydantic Models and Type Annotations">

<KeyIdea>
Pydantic uses standard Python type annotations to validate data types, parse strings, and enforce structural contracts.
</KeyIdea>

```python
from pydantic import BaseModel, Field

class CourseEnrollment(BaseModel):
    course_code: str = Field(..., min_length=3, max_length=10)
    credits: int = Field(default=4, ge=1, le=8)
```

If a client sends JSON with `"credits": "4"`, Pydantic automatically coerces the string `"4"` into the integer `4`. If the client sends `"credits": "four"`, validation fails immediately.

</TopicSection>

<TopicSection id="custom-validators" title="3. Field Constraints and Custom @field_validator">

<KeyIdea>
Domain-specific business invariants are cleanly isolated into `@field_validator` functions that sanitize or reject inputs.
</KeyIdea>

```python
@field_validator("cgpa")
@classmethod
def round_cgpa(cls, v: float) -> float:
    if v < 0 or v > 10:
        raise ValueError("CGPA must be between 0.0 and 10.0")
    return round(v, 2)
```

Custom validators execute during schema parsing, keeping database and service layers free from basic validation logic.

</TopicSection>

<TopicSection id="nested-schemas" title="4. Nested Schemas and Serialization (ORM Mode)">

<KeyIdea>
Pydantic models can be composed into hierarchical trees that mirror complex database relationships.
</KeyIdea>

```python
class DepartmentSchema(BaseModel):
    name: str
    hod: str

class ProfessorSchema(BaseModel):
    name: str
    department: DepartmentSchema
```

Setting `from_attributes = True` allows FastAPI to serialize SQLAlchemy model instances directly:

```python
@app.get("/professors/{id}", response_model=ProfessorSchema)
def get_prof(id: int, db: Session = Depends(get_db)):
    prof_model = db.query(Professor).get(id) # SQLAlchemy instance
    return prof_model # Pydantic reads attributes automatically
```

</TopicSection>
