  - question: "What is the difference between a Message Broker and a Result Backend in Celery?"
    answer: "A Message Broker (e.g. Redis, RabbitMQ) transports task invocation messages from the producer to workers. A Result Backend (e.g. Redis, PostgreSQL) stores the return values, task status, and exceptions after the task completes."
    explanation: "If you only need fire-and-forget tasks (like sending emails) where the return value isn't read later, you can run Celery without a result backend."
  - question: "Why must Celery tasks be idempotent?"
    answer: "Because in distributed systems with network drops or worker crashes, the broker may re-deliver a task message, causing the task to execute multiple times."
    explanation: "Idempotency ensures that running the task twice (e.g. processing a payment or charging a fee) produces the same outcome as running it once."

<TopicSection id="blocking-io-problem" title="1. The Synchronous Web Request Bottleneck">

<KeyIdea>
HTTP request-response lifecycles are designed for sub-second responses; executing multi-second operations synchronously degrades server capacity.
</KeyIdea>

Consider generating an end-of-term PDF grade sheet for **1,500 students**:
- Generating the PDF takes **18 seconds**.
- An HTTP worker thread is tied up for the entire 18 seconds.
- If 10 students request grade sheets concurrently, all 10 web worker threads freeze, rendering the website completely inaccessible to other users.

Offloading tasks to background worker processes solves this bottleneck.

</TopicSection>

<TopicSection id="celery-architecture" title="2. Celery Distributed Task Queue Architecture">

<KeyIdea>
Celery decouples user request handlers from heavy processing tasks using a producer-broker-consumer pipeline.
</KeyIdea>

```
[ User Browser ]
       │ HTTP POST /generate-report
       ▼
[ Web App (FastAPI / Flask) ] ── (task.delay()) ──> [ Message Broker (Redis) ]
       │                                                      │
  (Returns 202 Accepted & task_id)                            ▼
       │                                            [ Celery Worker Pool ]
       ▼                                                      │
[ Poll Status /api/tasks/{task_id} ] <────────────── [ Result Backend ]
```

The web server returns an HTTP `202 Accepted` status with the `task_id` in less than **10 milliseconds**, and the user sees a progress bar while the Celery worker computes in the background.

</TopicSection>

<TopicSection id="broker-and-backend" title="3. The Roles of Message Broker vs Result Backend">

<KeyIdea>
The broker manages in-flight message queues; the result backend stores historical execution state.
</KeyIdea>

- **Message Broker (e.g. Redis DB 0 / RabbitMQ)**: Acts as a buffer. If 500 tasks arrive simultaneously, the broker holds them safely in memory until available workers consume them.
- **Result Backend (e.g. Redis DB 1 / PostgreSQL)**: Stores task outcomes:
  - `state: "PENDING" | "STARTED" | "SUCCESS" | "FAILURE"`
  - `result: { "download_url": "/static/reports/term1.pdf" }`

</TopicSection>

<TopicSection id="task-retries-failure" title="4. Designing Robust Tasks: Exponential Backoff & Idempotency">

<KeyIdea>
Background tasks must expect network failures and apply exponential backoff retries to avoid overwhelming struggling third-party APIs.
</KeyIdea>

```python
# Exponential backoff pattern
@celery_app.task(bind=True, max_retries=5)
def sync_grades_with_canvas(self, grade_id):
    try:
        remote_api.sync(grade_id)
    except ConnectionError as exc:
        # Delays: 10s, 20s, 40s, 80s, 160s
        delay = 10 * (2 ** self.request.retries)
        raise self.retry(exc=exc, countdown=delay)
```

Pairing exponential backoff with idempotency tokens guarantees that transient network errors self-heal automatically without human intervention.

</TopicSection>
