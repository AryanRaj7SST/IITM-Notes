<TopicSection id="enterprise-data" title="1. Data as an Enterprise Asset & OLTP vs OLAP">

<KeyIdea>
Modern enterprise architectures decouple real-time transactional processing (OLTP) from multi-dimensional analytical intelligence (OLAP) to balance low-latency writes against compute-intensive aggregation.
</KeyIdea>

In an enterprise such as a national supermarket chain handling **50,000 active SKUs** and **12,000 transactions per minute**, data serves two fundamentally different business functions:

```
Operational Pipeline:
[ Point-of-Sale POS ] ──> [ OLTP: PostgreSQL / MySQL ] 
                                  │ (Nightly ETL / CDC Stream)
                                  ▼
[ Executive Dashboard ] <── [ OLAP: Snowflake / ClickHouse / BigQuery ]
```

### Comparative Framework: OLTP vs. OLAP

| Feature Dimension | OLTP (Online Transaction Processing) | OLAP (Online Analytical Processing) |
| :--- | :--- | :--- |
| **Primary Goal** | High concurrency, real-time data integrity | Long-term trend analysis, executive reporting |
| **Query Pattern** | Simple point-reads and single-row writes (`INSERT`, `UPDATE`) | Heavy aggregations (`SUM`, `AVG`, `GROUP BY`) over millions of rows |
| **Schema Design** | Highly normalized (3NF / BCNF) to eliminate redundancy | Denormalized Star or Snowflake dimensional schemas |
| **Latency Benchmark** | Strict sub-second response ($< 15\text{ ms}$) | Seconds to minutes acceptable |
| **Typical Example** | Recording a credit card charge of ₹1,499 | Calculating year-over-year revenue growth across regions |

<CheckBadge reason="Transcript mentioned 'OLAP handles customer login sessions'. Corrected: Login authentication is strictly an OLTP transactional workload." />

<AddedByTutor>
In modern data engineering, the transition from OLTP to OLAP is managed using **Change Data Capture (CDC)** tools like Debezium, streaming row-level WAL (Write-Ahead Log) mutations directly into analytical lakes.
</AddedByTutor>

<TopicSection id="relational-model" title="2. The Formal Relational Model & Codd's Rules">

<KeyIdea>
Edgar F. Codd formulated the relational model in 1970 to liberate application software from the physical layout of disk storage through mathematical set theory and first-order predicate logic.
</KeyIdea>

### Formal Academic Definition
> **Relation**: Given domains $D_1, D_2, \dots, D_m$, a relation $R$ is a subset of the Cartesian product $D_1 \times D_2 \times \dots \times D_m$. A tuple $t \in R$ is an ordered list of values $\langle v_1, v_2, \dots, v_m \rangle$ such that $v_j \in D_j$.

### Plain-Language Breakdown
> Think of a **relation** simply as a 2D spreadsheet or table where:
> - Every column represents a typed attribute (e.g. `customer_id`, `email`).
> - Every row represents an individual, unique record (a tuple).
> - Duplicate rows are strictly forbidden.
> - The physical order in which rows or columns appear has zero semantic meaning.

<TopicSection id="integrity-constraints" title="3. Integrity Constraints: Entity, Referential, & Domain">

<KeyIdea>
Integrity constraints act as automated database-level guardrails, ensuring that data stored within tables satisfies predefined business invariants at all times.
</KeyIdea>

Relational systems enforce three primary classes of constraints:

1. **Entity Integrity**:
   - The primary key cannot contain a `NULL` value.
   - Every tuple must be uniquely distinguishable via its primary key attribute(s).

2. **Referential Integrity**:
   - A Foreign Key (FK) in a referencing table must either be completely `NULL` or match an existing Primary Key (PK) value in the referenced parent table.
   - Enforces valid business relationships (e.g., an Order cannot belong to a non-existent Customer).

3. **Domain Constraints**:
   - Values in an attribute column must belong to the declared domain (e.g., `total_amount > 0.00`, `tier_level IN ('Bronze', 'Silver', 'Gold')`).

### Referential Action Cascade Options:
```sql
ALTER TABLE orders
  ADD CONSTRAINT fk_customer
  FOREIGN KEY (customer_id) 
  REFERENCES customers(customer_id)
  ON UPDATE CASCADE
  ON DELETE RESTRICT;
```
- `ON UPDATE CASCADE`: If a customer ID is updated, all associated order records update automatically.
- `ON DELETE RESTRICT`: Prevents deletion of a customer who has existing historical orders in the system.

</TopicSection>

<TopicSection id="acid-guarantees" title="4. The ACID Framework in Enterprise Transactions">

<KeyIdea>
ACID guarantees form the bedrock of database reliability, ensuring mission-critical financial and logistical operations retain consistency in the presence of failures and high concurrency.
</KeyIdea>

Consider transferring **₹5,000** from Account A to Account B:

$$\text{T1}: \quad \text{Read}(A) \implies A := A - 5000 \implies \text{Write}(A) \implies \text{Read}(B) \implies B := B + 5000 \implies \text{Write}(B)$$

### The Four ACID Pillars:

- **Atomicity (All-or-Nothing)**:
  - If the server crashes after debiting $A$ but before crediting $B$, the database Write-Ahead Log (WAL) undoes the debit. Either the entire sequence commits, or none of it does.
- **Consistency (Preserving Invariants)**:
  - Total money across $(A + B)$ before the transaction must equal $(A + B)$ after the transaction.
- **Isolation (Concurrency Shielding)**:
  - An independent concurrent transaction T2 cannot view intermediate, uncommitted states where $A$ has been deducted but $B$ has not yet been credited.
- **Durability (Fault Survival)**:
  - Once the transaction manager returns a `COMMIT` acknowledgment to the application, the changes persist across power failures and system crashes.

</TopicSection>
